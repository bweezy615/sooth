# The Odds API is rejecting our key — needs Branden, not a code fix

*Found during the 2026-09-07 unattended session, read-only. Nothing in this
repo was changed to address it — see "Why this is not mine to fix" below.*

## What's happening

Since roughly **2026-09-07 06:36 UTC**, every call to api.the-odds-api.com —
including `GET /v4/sports/`, which `engine/lines.py` calls "free" — has
returned **401 Unauthorized**. This is not a quota message wrapped in a 401:
the board published at 06:34:48 UTC that morning reported
`credits_remaining: 19256` of what memory says is a 20,000/mo plan, and the
API was consuming about 5 credits per 30-minute run before that — nowhere
close to exhausted.

Confirmed across three independent workflows, all hitting 401 on the same
call from ~12:19 UTC onward:

- `props-live.yml` — run `34121232958` (12:19), `34152662363` (18:41).
  `engine.props` fails on `active_sports()`, and this workflow already has
  the "fail loudly if the board didn't refresh" guard added 2026-08-28
  (`scheduled-runs-and-silent-green.md`), so it is correctly showing **red**
  in Actions.
- `capture-props.yml` — run `34123062699` (12:39), `34152871217` (18:44).
  No guard at all on this job (also by 2026-08-28 design) — correctly **red**.
- `capture.yml` ("capture-odds") — run `34121614946` (12:23),
  `34151266611` (18:21). The Odds-API step (`engine.lines`) hits the same 401
  on the same `active_sports()` call, but the job still shows **green**
  because that step carries `continue-on-error: true` and the unrelated free
  ESPN capture step still succeeds. This is the documented, deliberate design
  in `scheduled-runs-and-silent-green.md` §1 ("capture.yml: fine,
  deliberately"), not a new bug — but it means the green checkmark on this
  workflow does not currently mean the board refreshed.

Net effect on the live site: `site/public/data/board.json` has not updated
since the `db72ab48` commit (`generated_at: 2026-09-07T06:34:48Z`) as of this
writing — call it half a day stale during an actual NFL Sunday. `props.json`
and the edges/middles Odds-API half are in the same state, for the same
reason (`edges.yml`'s middles step carries the same kind of guard, so its
green status also doesn't confirm a live pull happened).

## Why this is not mine to fix

- **The repo's secret hasn't changed.** `gh secret list` shows `ODDS_API_KEY`
  last updated 2026-08-04 — three and a half weeks before this started. No
  workflow file changed today either. The failure is on the-odds-api.com's
  side: the key it issued us is being rejected by their service, not
  misconfigured by us.
- **A 401 on their nominally free endpoint rules out the one explanation a
  repo change could paper over** (a code bug spending credits too fast) —
  the balance was healthy hours before this started.
- Hard rule for this repo: never request, echo, or touch the six secrets.
  Whatever the actual cause on their end (billing hiccup, suspected-abuse
  flag, a support action, a plan change) it can only be seen and fixed from
  the-odds-api.com's own account dashboard, which only Branden can reach.

## What Branden needs to do

Log into the-odds-api.com's account dashboard and check for:
1. An account/billing notice (the plan lapsing, a payment failure, a
   suspension notice).
2. Whether the key shown there still matches what's in this repo's
   `ODDS_API_KEY` GitHub secret (Settings → Secrets and variables → Actions
   — the value can't be read back, only replaced, so compare by regenerating
   if there's any doubt and pasting the new one in).
3. Their status page / support channel, in case this is a wider outage.

Nothing needs re-running once the key is fixed — `capture.yml`,
`capture-props.yml`, `props-live.yml` and `edges.yml` are all on schedules of
30 minutes to 2 hours and will pick the board back up on their own next tick.
No re-seal, no backfill; the gap is a hole in `data/capture/*.jsonl` for
however long this lasts, same as any other missed capture window.

## One more thing worth deciding, not urgent

`capture.yml`'s `continue-on-error: true` on the Odds-API step was a
deliberate 2026-08-28 choice, reasoned as: a *transient* Odds API hiccup
shouldn't cost the free ESPN capture that runs in the same job. That reasoning
holds for a five-minute blip. It is quietly weaker for a *sustained*, hours-long
outage like this one, where the workflow will keep reporting green every 30
minutes with the board frozen and nobody would see it going stale from the
Actions tab alone — they'd have to check `board.json`'s own `generated_at`, the
way this session did. Not changing it today: `props-live.yml` and
`capture-props.yml` already surface this specific outage loudly, so nothing
was actually silent this time. Flagging only because "one of three guards
would have missed it" is worth Branden's eyes if he wants the same
fails-after-N-consecutive-misses treatment `edges.yml`/`props-live.yml` got
in `scheduled-runs-and-silent-green.md` applied to `capture.yml`'s board step
too.
