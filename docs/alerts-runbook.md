# Alerts — how it works, and what has to be true for it to send

Built 2026-08-22, closing item #7 on the competitive build list — ranked there
as the **worst** absence we had: *"Every paid product in both segments ships
them, and they are the single most-cited reason people pay for these tools at
all. A product with no reason to return has no retention."*

---

## The shape

Three things get emailed, and nothing else ever will:

| Kind | Fires from | Cadence | Content |
|---|---|---|---|
| `seal` | `seal.yml`, after the anchor commit is pushed | Wednesdays in season | slate id, game count, first kickoff, Merkle root, commit URL |
| `graded` | `grade.yml`, from the step that publishes the result | Tuesdays in season | record per model, Brier, CLV or the reason there is none |
| `price` | `alerts.yml`, twice an hour | whenever a book is out of line | the divergences that clear *that subscriber's* threshold |

Alerts are **free and opt-in**. They are not a Pro feature and PRODUCT.md now
says so. The previous wiring took its recipients from active Stripe
subscriptions, which — with Pro disarmed — is an empty set by construction:
the most-requested feature in the whole competitive scan was connected to
nobody and would have stayed that way silently.

## The pieces

```
site/public/alerts.html   the signup surface (/alerts)
api/alerts.js             POST signup · GET confirm · GET+POST unsubscribe · prefs
api/_auth.js              the HMAC token scheme (already existed)
engine/alert_token.py     the same scheme in Python, for links minted in Actions
engine/subscribers.py     read the list; per-person kinds + threshold
engine/mailer.py          one email shell, one send path, unsubscribe headers
engine/alert_email.py     price divergence (rewritten for per-person thresholds)
engine/alert_lifecycle.py seal + graded
data/alerts_sent.json     price watermark: alert key -> magnitude last sent at
data/lifecycle_sent.json  seal/graded watermark: one key per slate
```

## Where the list lives, and why there

**Stripe customer metadata.** Not a repo file (subscriber addresses in a public
git history are permanent and encryption does not undo a key leak), not a new
private repo (a token in two places, a read-modify-write race per signup), not
Resend contacts (its audiences API is mid-migration to segments and none of it
is testable locally). Stripe costs nothing new: the key is already configured
in Vercel *and* in Actions, and a customer with no subscription is free.

Metadata keys, which `api/alerts.js` writes and `engine/subscribers.py` reads —
change one and you must change both:

```
sooth_alerts        "1" opted in · "0" unsubscribed   (anything else = not a subscriber)
sooth_kinds         comma list from {seal, graded, price}
sooth_min_pts       float, 1.5–10.0, price threshold in points of implied probability
sooth_confirmed_at  ISO8601 — when they clicked the confirm link
sooth_source        "alerts-page"
```

Unsubscribing flips the flag and never deletes the record, so an opt-out cannot
be lost by someone re-adding the address later.

## ⚠ Before this can send: one secret, one place

Checked live on 2026-08-22:

| Secret | Vercel | Actions | Needed for |
|---|---|---|---|
| `STRIPE_SECRET_KEY` | ✅ | ✅ | the list itself |
| `RESEND_API_KEY` | ✅ | ✅ | sending |
| `AUTH_SECRET` | ✅ | ❌ **missing** | signing the unsubscribe link |

Signup already works end to end on sooth.bet — a POST to `/api/alerts` returns
`{"ok":true,"sent":true}` and mails a confirmation. What cannot run yet is the
**Actions** side: `engine.alert_token` refuses to mint an unsubscribe link
without `AUTH_SECRET`, so `alert_email` and `alert_lifecycle` exit without
sending rather than mail a dead opt-out link.

**Fix:** GitHub → repo Settings → Secrets and variables → Actions → New secret.
Name `AUTH_SECRET`, value **exactly** the string already set in the Vercel
project (Vercel → Settings → Environment Variables). It has to match
character-for-character: a link signed in Actions with a different secret fails
verification in Vercel, and the unsubscribe button silently does nothing.

Until then the system **fails closed and stays honest** — it does not send.

Verify after setting it:

```bash
gh workflow run send-alerts
```

then `gh run list --workflow=send-alerts --limit 1`, and check the log says
`sent N/M` rather than the AUTH_SECRET refusal.

## Checks

```bash
node api/alerts.selfcheck.js
python -m engine.alert_email --selfcheck
python -m engine.alert_lifecycle --selfcheck
python -m engine.alert_lifecycle --kind seal --dry-run
python -m pytest tests/test_alert_subs.py -q
python -m engine.subscribers --kind price     # needs STRIPE_SECRET_KEY; prints the list
```

`test_alert_subs.py` pins a signature vector generated by `api/_auth.js`. If it
fails, the Python and Node halves of the link scheme have drifted and **every
unsubscribe link already sitting in a mailbox has stopped working** — fix the
drift, do not update the vector.

## Design decisions worth not re-litigating

**Double opt-in, and nothing is stored on POST.** A stranger who types someone
else's address causes exactly one confirmation email to that person and creates
no record. Storing on POST would make this endpoint a subscription-bombing
tool. It is also the reason there is no rate limiting here yet — worth adding
if the confirmation endpoint is ever abused in volume.

**The scan runs once at the lowest threshold anyone chose**, then each alert is
filtered per person. Scanning per subscriber would re-read the whole capture
history once per subscriber.

**The watermark stores magnitude, not just identity.** A divergence that grows
from 2 points to 6 must reach the person who only wanted 4+, without re-telling
the person already told at 2. `RESEND_STEP` (1.0 pt) is the bar for "this is
genuinely bigger now" rather than a reprice. The old list-of-keys format loads
as `+inf` — already spoken for — so the upgrade cannot mail the back catalogue
to the first subscriber.

**No addresses in the watermark.** It is committed to a public repo.

**The lifecycle emails ship from the seal and grade jobs themselves**, not from
a separate workflow. `grade.yml` already has an assertion step forcing a sealed
slate past settle time to be graded; mailing from the same job means there is
no button for someone to not press on a bad week.

## Known limits

- **Frequency is real and high in season.** 160 divergences cleared 2.0 points
  in the 12 days to 2026-08-22 across MLB game lines and props — about 13/day.
  `/alerts` states this measured figure rather than a promise, and offers a 4+
  band. If subscribers still complain, the fix is a digest, not a quieter lie.
- **Stripe customer search is eventually consistent** (up to ~1 min). A brand
  new subscriber can miss the very next tick; `fetch()` falls back to a full
  list scan when search returns nothing.
- **No bounce or complaint handling.** Resend records them; we do not read them
  back, so a hard-bouncing address stays on the list. Worth wiring a Resend
  webhook to flip `sooth_alerts` to `0` before volume makes it matter.
