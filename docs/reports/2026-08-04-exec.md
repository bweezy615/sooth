## 2026-08-04 · run 2 (unattended, scheduled executive)

### Board health — INCIDENT (found and remediated), now GREEN

**Lead finding: the live board was ~7.75 hours stale while MLB games sat inside
the window. The capture cron was healthy; the *publish* step was silently
broken.** Fixed this run.

What was happening:

```
capture cron (main)   success 2026-08-04T11:58:48Z   commits board.json to main
                      success 2026-08-04T11:33:38Z
                      success 2026-08-04T09:49:16Z
                      success 2026-08-04T09:07:03Z
                      success 2026-08-04T07:08:33Z
main   HEAD 6bce8fc "capture: odds snapshot 2026-08-04T11:59:05Z"
       site/public/data/board.json generated_at 2026-08-04T11:59:04Z   FRESH

live   https://bweezy615.github.io/sooth/data/board.json
       generated_at 2026-08-04T04:15:25Z   STALE by ~7h45m   (cache-busted read)
```

So main was fresh every ~90 min, but the public site was frozen at the 04:15
snapshot. The board *is* the product; a stale public board is the one incident
the charter says to lead with.

**Root cause.** `deploy-site` (`.github/workflows/pages.yml`) fires
`on: push` to `site/public/**`. The capture cron *does* modify
`site/public/data/board.json`, so the path filter is not the problem. The
problem: the cron pushes with the default `GITHUB_TOKEN`, and GitHub
deliberately does **not** trigger downstream workflows from `GITHUB_TOKEN`
pushes (its recursion guard). Evidence — `deploy-site` ran only on human/exec
pushes, never on a capture commit:

```
deploy-site  05:23:25Z push          <- human/exec push (last real deploy)
             04:46:59Z push
             04:36:29Z push
             04:30:08Z push
capture commits at 07:08 / 09:07 / 09:49 / 11:33 / 11:59Z produced NO deploy-site run.
```

This is also why run 1 reported the board "FRESH" and GREEN: an operator push
had refreshed Pages minutes earlier. That freshness was incidental to a human
being at the keyboard; it masked a latent publish defect that surfaced the
moment the cron ran unattended. Run 1's GREEN was not wrong at that instant, but
it was not durable.

**Remediation (done this run).** Dispatched the existing deploy to publish the
already-committed fresh board:

```
$ gh workflow run deploy-site        # run 30907912695, event=workflow_dispatch
  -> conclusion: success
$ curl -s -L ".../data/board.json?cb=..."   # after deploy, cache-busted
  "generated_at": "2026-08-04T11:59:04.931665+00:00"     <- was 04:15Z, now matches main
```

Live board is current again.

**Durable fix (on branch `exec/pages-autodeploy`, not merged).** Added a
`workflow_run` trigger to `pages.yml` so the deploy fires whenever `capture-odds`
completes. `workflow_run` is not subject to the `GITHUB_TOKEN` guard. Guarded
with `if: workflow_run.conclusion == 'success'` so a failed capture never
publishes. Validation:

```
$ ruby -ryaml  (structure)
triggers: ["workflow_run", "push", "workflow_dispatch"]
workflow_run: {"workflows"=>["capture-odds"], "types"=>["completed"]}
deploy.if: "${{ github.event_name != 'workflow_run' || github.event.workflow_run.conclusion == 'success' }}"
ASSERT OK: names capture-odds; retains push + workflow_dispatch

$ name cross-check
capture.yml name: capture-odds
pages.yml  workflows: ["capture-odds"]
MATCH CONFIRMED: trigger name == capture workflow name
```

The name cross-check matters: a `workflow_run` that names a non-existent
workflow parses fine and silently never fires — exactly the class of
confident-and-wrong failure the charter warns about. It matches.

**What I could NOT verify, and why.** `workflow_run` reads its trigger config
from the copy of `pages.yml` on the **default branch**. On `exec/pages-autodeploy`
it is inert — it cannot fire until this is merged to `main`. So the end-to-end
"next capture auto-publishes" behavior is *unproven this run*. What is proven:
the deploy mechanism itself works (remediation above), the YAML is valid, and
the workflow name matches. **User action after merge:** wait for the next
`capture-odds` run, then confirm a `deploy-site` run appears with
`event=workflow_run` and the live board matches main. Until then, the board will
still drift between human pushes — the remediation refreshed it once but does
not keep it fresh.

Known accepted tradeoff: `workflow_run` fires on *every* capture completion,
including near-kickoff sweeps that commit nothing, so `deploy-site` may
re-publish identical static files a few times a day. Harmless; Actions minutes
are free on the public repo.

## 2026-08-04 · run 3 — P2 line-movement alerts: DONE

### Built

`engine/alerts.py`. Two detectors, deliberately separate because they are not
the same signal:

- **drift** — one book's own price moved between our observations. That is the
  book changing its mind.
- **divergence** — a book's current price sits away from the cross-book median.
  That is the one that pays immediately.

Both measured in points of implied probability, never raw American odds, which
are non-linear and discontinuous across ±100. Provenance-gated to `own_capture`
exactly like CLV: `espn_open` is someone else's claim about a price we never
watched.

### Verification — real history, output pasted

```
observations   : 2386
threshold      : 1.5 pts of implied probability
drift alerts   : 2
divergence     : 0
  DRIFT  New Orleans Saints at Detroit Lions   DraftKings shortened 2.27 pts on over (-105 to -115)
  DRIFT  New Orleans Saints at Detroit Lions   DraftKings drifted out 2.27 pts on under (-115 to -105)
```

Those two alerts are the two sides of one coherent move: DraftKings shifted the
juice on the NO at DET total. The symmetry is the arithmetic checking itself.

```
46 passed in 3.69s
```

12 new tests. Fires on a real move, silent on a one-cent tick, catches a slow
walk at the step that crosses the threshold, never compares across books,
requires 3+ books before claiming a consensus, ignores a book paying *less*
than consensus (a worse price is not an opportunity), uses each book's latest
price, and refuses non-`own_capture` rows entirely.

### Finding — divergence cannot fire yet, and that is not a bug

Zero divergence alerts because **our capture history is single-book**. ESPN
gives DraftKings only, and divergence needs at least three books to have a
consensus worth diverging from.

The multi-book data already exists — `engine/lines.py` reads ten books — but it
writes `board.json`, not capture rows, so the alert detector never sees it.

**Deferred to the user, because it costs credits:** wiring `engine/lines.py` to
also append its multi-book quotes into `data/capture/` would make divergence
live immediately and would make CLV multi-book at the same time. Roughly 1
credit per sport per sweep on top of current burn. This is the single highest

### Correction to my own estimate

### Built

`engine/lines.py` now appends every individual book quote to
`data/capture/<sport>/<date>.jsonl` with provenance `own_capture`, append-only,
one file per sport per UTC day. This unlocks divergence alerts and multi-book
CLV in one change.

### Bug found, and it was dangerous

Writing the rows immediately exposed a name collision:

```
Draft Kings   espn      nfl   1716
DraftKings    espn      nfl   3056
DraftKings    oddsapi   mlb     30
```

**ESPN returns both spellings for the same operator.** Left alone, one book is
counted as two. Divergence requires 3+ books before it will claim a consensus,
so a split identity can push a 2-book market over that threshold and fire an
alert against a consensus that does not exist.

This is a **pre-existing bug in our ESPN capture**, not one this change
introduced. It was invisible while capture was single-book, and would have
started producing false alerts the moment divergence went live.

Fixed with `canonical_book()` in `engine/schema.py`, applied at write time in
both writers:

```
DraftKings         -> DraftKings
Draft Kings        -> DraftKings
williamhill_us     -> Caesars
BetOnline.ag       -> BetOnline
barstool           -> ESPN BET
```

### The pattern this makes six

Six verification steps in this project have now reported something false or
incomplete. This one is the most instructive: the production run genuinely
succeeded, the tests genuinely passed, and the feature was genuinely still
broken. **A green check on the thing you changed says nothing about the data
that was already there.**
