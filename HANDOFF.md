For the person building the app. Everything you need is here or linked from
here. Read section 1 before you write any UI copy, because it constrains what
the product is allowed to say.

## 1. The one thing you must understand first

**Our model does not beat the betting market. We know this, we measured it, and
we publish it on the front page.**

Walk-forward backtest, out-of-sample, leakage-controlled:

| | n | Brier | ATS | vs 52.38% break-even |
|---|---|---|---|---|
| Our independent model | 2,671 | 0.22148 | 49.50% | loses |
| Closing market | 2,671 | 0.21038 | 50.88% | loses |
| Our model (real closes) | 854 | 0.22164 | 48.74% | loses |

We tested a second sport with completely independent data (EPL, documented
closing odds) and got the same answer: Brier 0.57961 vs market 0.56444.

**Two sports, two data sources, same verdict.** This is not a bug to be fixed
before launch. It is the honest state of the art for a small operation, and
almost certainly for the large ones too — they simply do not publish it.

### So what are we actually selling?

**Verifiability, not edge.** Every prediction is hashed into a Merkle
commitment *before* kickoff, revealed after, and graded in public including the
losses. Anyone can recompute the hash and prove we changed nothing. Nobody else
in this category does that, because publishing a real record makes their
claimed edge falsifiable.

The one thing we are genuinely good at is **calibration** — when we say 70%,
it happens about 70% of the time. Our consensus model's calibration error is
0.01858 against the market's 0.01913, i.e. slightly *better* than the market.
Calibration and profitability are different properties. Conflating them is the
central dishonesty of this industry and we do not do it.

## 2. Hard rules — these are not style preferences

Breaking any of these is a legal or existential problem, not a bug.

1. **Never accept, place, or facilitate a wager. Never hold customer funds or
   pay prizes.** This single fact is what keeps us a publisher rather than a
   gambling operator, and keeps us inside Stripe's and Apple's rules. Every
   other gate opens on it.
2. **Never make a performance claim that isn't regenerated by
   `scripts/published_figures.py`.** If a number can't be produced by that
   command, it does not go in the app. FTC substantiation is the binding
   constraint here, not gaming law, and "AI" branding puts us inside the FTC's
   stated enforcement focus.
3. **Banned words, everywhere in the UI:** *guaranteed, lock, risk-free,
   insider, sure thing.* Also no win-rate or ROI claims we can't reproduce on
   demand from the ledger.
4. **Never present the consensus model as "our prediction" on its own.** It
   takes the market price as an input, so it looks smart while carrying almost
   no independent information. Both models ship, labelled. See §5.
5. **Never show a confidence above 85%.** Our top band measured 94.5%
   predicted vs 86.7% actual. The cap is deliberate and the methodology page
   explains it.
6. **Never edit or delete a published prediction.** Corrections are new
   versions with a `supersedes` pointer. A root that silently vanishes is
   indistinguishable from tampering.
7. **Age-gate 18+, and show responsible-gambling info.** NCPG helpline
   **1-800-522-4700**, 24/7.
8. **Android caveat:** Google Play forbids gambling ads inside an app that
   also provides odds/score tracking. Affiliate ad units and an odds product
   are mutually exclusive on Play — pick one.

Full disclaimer set: `site/content/disclaimers.md` (9 items, ready to use).

## 3. Architecture

```
data sources ──▶ adapters ──▶ engine ──▶ commitment ──▶ JSON ──▶ app / site
   (free)      (per sport)   (models)    (Merkle)      (static)
```

Everything is **static JSON on a CDN**. There is no backend server, no
database, no auth. The app is a reader. That is deliberate: it makes the data
independently verifiable, cheap to host, and impossible to quietly mutate.

```
engine/
  schema.py       Event / Line / Prediction / Result + odds maths
  commit.py       SHA-256 Merkle commit-reveal. The differentiator.
  calibrate.py    isotonic calibration
  backtest.py     walk-forward scoring vs the de-vigged market
  closing.py      consensus closing lines from the paid backfill
  capture.py      live odds capture (runs on GitHub Actions)
  backfill.py     historical closing lines (Odds API, already run)
  grade.py        grades a revealed slate; provenance-gated CLV
  features.py     opponent-aware EPA ratings
  models/
    elo.py        Elo + margin-of-victory
    ensemble.py   the two published models
  adapters/
    base.py       the contract a new sport implements
    nfl.py        nflverse
    epl.py        football-data.co.uk
  pipeline/
    weekly.py     predict -> calibrate -> cap -> seal -> publish
data/
  ledger/         commitments + reveals (the public record)
  capture/        our own timestamped odds observations
  backfill/       purchased historical closing lines
site/public/      static site + the JSON the app reads
tests/            34 tests
```

## 4. Data contracts — what the app consumes

### 4.1 Weekly slate — `/data/{season}-W{week:02d}-{sport}.json`

Example: `https://sooth.co/data/2026-W01-nfl.json`

```json
{
  "slate_id": "2026-W01-nfl",
  "sport": "nfl",
  "season": 2026,
  "week": 1,
  "status": "committed",
  "models": {
    "independent": {
      "version": "elo+epa-v1+iso",
      "description": "Elo + opponent-aware EPA + rest. Does not see the betting line. This is our own opinion.",
      "backtest_brier": 0.22164,
      "backtest_ece": 0.03269
    },
    "consensus": {
      "version": "elo+epa+market-v1+iso",
      "description": "The same features plus the de-vigged market probability. Best calibrated, but largely reproduces the market.",
      "backtest_brier": 0.21399,
      "backtest_ece": 0.01858
    }
  },
  "confidence_cap": 0.85,
  "merkle_root": "4136512c…",
  "committed_at": "2026-08-03T05:05:48Z",
  "earliest_kickoff": "2026-09-09T20:20:00Z",
  "n_predictions": 32,
  "games": [
    {
      "game_id": "2026_01_NE_SEA",
      "kickoff": "2026-09-09T20:20:00+00:00",
      "home": "SEA",
      "away": "NE",
      "independent": { "pick": "SEA", "prob": 0.6466, "fair_odds": -183 },
      "consensus":   { "pick": "SEA", "prob": 0.7030, "fair_odds": -237 },
      "market_prob": 0.6369,
      "spread_line": 3.5,
      "models_disagree": false,
      "independent_vs_market": false
    }
  ],
  "disclaimer": "Analysis and entertainment only. We do not accept wagers…"
}
```

Field notes that matter for the UI:

- `prob` is **already capped at 0.85** and is the probability of *that pick*
  winning, not of the home team winning. Don't re-derive it.
- `fair_odds` is American odds implied by our probability with no vig. It is
  useful as a comparison against a book's price. It is **not** a price we
  offer, because we offer nothing.
- `market_prob` is the **de-vigged** market probability for the **home** team.
  Note the asymmetry with `prob` — this trips people up.
- `models_disagree` = the two models picked different sides. Interesting, worth
  surfacing, not a signal.
- `independent_vs_market` = our independent model disagrees with the market.
  **Display this as a caution, not a tip.** Early season our ratings know
  nothing about free agency, the draft, or QB changes, which the market prices
  instantly. See §6.
- `spread_line` is stated from the home perspective (positive = home favoured).

### 4.2 Commitment — `/data/{slate_id}.commitment.json`

```json
{
  "algorithm": "sha256-merkle-v1",
  "slate_id": "2026-W01-nfl",
  "sport": "nfl",
  "version": 2,
  "supersedes": "d081c00f…",
  "merkle_root": "4136512c…",
  "n_predictions": 32,
  "committed_at": "2026-08-03T05:05:48Z",
  "earliest_kickoff": "2026-09-09T20:20:00Z"
}
```

Predictions may legitimately be revised **until kickoff**; each revision is a
new version pointing at the root it supersedes. All versions are retained and
independently verifiable forever. If you build a "verify" screen, let the user
check any version, not just the latest.

### 4.3 Odds observation (internal, for reference)

```json
{
  "observed_at": "2026-08-03T03:53:21Z",
  "provenance": "own_capture",
  "sport": "nfl", "season": 2026, "week": 1,
  "event_id": "401872656",
  "home": "Seattle Seahawks", "away": "New England Patriots",
  "book": "DraftKings",
  "market": "spread", "selection": "side_a",
  "line": -3.5, "price": -110
}
```

**`provenance` is load-bearing.** Only `own_capture` (we watched it, timestamped)
and `oddsapi_historical_close` (we paid for it) may contribute to a published
closing-line-value number. `espn_open`, `espn_close`, `nflverse_consensus` are
recorded but are someone else's claim and must never back a public CLV figure.

⚠️ **Three ID spaces exist and none agree.** Predictions use nflverse
`game_id` (`2026_01_NE_SEA`), capture rows carry ESPN ids (`401872656`),
backfill rows carry Odds API hashes. Join on `(season, home, away)` via the
team map in `engine/closing.py`. Getting this wrong silently reports "CLV
unavailable" forever, which looks exactly like a data gap. It already bit us
once.

## 5. How to present the two models

This is the most important UI decision in the product, and it's currently
**open** — see §8.

- **Independent** — Elo + opponent-adjusted EPA. Has never seen the line. This
  is genuinely our opinion. It is *worse* than the market and can disagree with
  it meaningfully.
- **Consensus** — same features plus the de-vigged market price. Best
  calibrated output we can produce, but it largely reproduces the market.

Publishing only the consensus would be market-following dressed as insight.
Publishing only the independent would throw away our best-calibrated estimate.
**Both ship, labelled, with the distinction explained** — that explanation is
itself the marketing.

## 6. Things that look like bugs but aren't

- **Big disagreements with the market in September.** Our ratings carry last
  season forward and know nothing about the offseason. The gaps should shrink
  as real data arrives. That convergence is a publishable story.
- **A terrible single week.** 2025 weekly accuracy ranged from **28.6%
  (Week 5) to 100% (Week 20)** against a 63.7% season average. In Week 5 the
  model's four most confident picks all lost. Single-week records are noise —
  and that's the strongest argument in the product for distrusting anyone
  quoting you one, including us.
- **CLV showing as unavailable.** Correct behaviour when we hold no qualifying
  pre-close reference price. We report the gap rather than estimating it.
- **Calibration slightly worsening Brier.** Isotonic trades sharpness for
  calibration. Both numbers get published.

## 7. Running it

Python 3.12 via `uv`; the venv is committed as config, not artefacts.

```bash
cd ~/pick-engine
uv venv --python 3.12 .venv
uv pip install pandas numpy scikit-learn requests pyarrow markdown pytest

python -m engine.backtest                       # elo baseline
python -m engine.models.ensemble                # 4-model comparison
python scripts/published_figures.py             # regenerate ALL site figures
python -m engine.pipeline.weekly --season 2026 --week 1   # seal a slate
python -m engine.grade --slate 2026-W01-nfl     # grade a settled slate
python scripts/epl_backtest.py                  # second sport
python scripts/build_site.py                    # render the static site
pytest -q                                       # 34 tests
```

**Automation already running:** `.github/workflows/capture.yml` captures odds
every 3 hours, and every 15 minutes inside the 90 minutes before any kickoff
(gated — zero HTTP when idle). It commits to the repo, so GitHub's commit
timestamps are third-party attestation that we held a given price at a given
time. Verified firing unattended.

**Secrets:** `.env`, gitignored. Currently `ODDS_API_KEY` (paid) and
`ODDS_API_KEY_FREE`.

## 8. Open decisions — not yet made

1. **Which model leads the UI** — Independent (honest, worse) or Consensus
   (calibrated, echoes the market). Editorial, with real consequences.
2. **Whether superseded commitments display by default.** Currently always
   visible. Maximally honest; also draws attention to a revision most users
   needn't care about.
3. **Keep or cancel the $30/mo Odds API subscription.** Backfill is done and
   permanent. Free ESPN gives ~1 book; paid gives 10 at ~2.3% of quota.
   Keeping it is what makes a *published* CLV number defensible.
4. **Monetisation.** Agreed direction: free tier = predictions + public record.
   Paid tier = **tools and data, explicitly not picks** (no-vig calculators,
   line-movement alerts, CLV lookups, model exports). Zero performance claims
   means zero FTC substantiation burden.
5. **Platform.** Web-first is live. Native app is your call — note Apple takes
   15–30% unless the current US external-link regime holds, and Play's ad
   restriction in §2.8.

## 9. Sport status

A sport ships **Live** only when we hold free, verifiable closing-line history
to grade it against. Otherwise **In calibration**, labelled unproven everywhere
it appears. Never mark a sport Live without that evidence.

| Sport | Status | Notes |
|---|---|---|
| NFL spread + total | Live-ready | graded vs purchased 17-book closes |
| NFL moneyline | In calibration | needs a season of our own capture |
| CFB spread + total | Board only | prices shipped; adapter built, no closing-line history yet |
| EPL 1X2 | In calibration | documented closing odds, better provenance than NFL |
| NBA / NHL | Not built | strong free closing-line history available |
| MLB | Not built | **source licence is NOASSERTION — legal review before any paid use** |
| UFC / Tennis | Not built | thin odds history |
| F1 / Cricket | Deferred | no free closing odds exist |

Adding a sport = implement `engine/adapters/base.py`. Nothing else. Adding EPL
required **zero** engine changes, which is the evidence the interface holds.
Note EPL emits a third `draw` selection — code assuming two outcomes will be
wrong there and should fail loudly rather than renormalise.

That claim holds for the model and backtest path. It does **not** hold for
`engine/pipeline/weekly.py`, which seals a slate: it imports `NFLAdapter`
concretely, reads `adapter.games` and `adapter._kickoff` rather than the
interface, and hardcodes `Sport.NFL` and the `-nfl` slate id. Sealing a second
sport means generalising that module first, and it writes the ledger, so it is
the one place where a hasty change is expensive — a root that moves or
disappears is indistinguishable from tampering (rule 6).

`engine/adapters/ncaaf.py` is implemented and tested against the cfbfastR
schedule mirror (free, no key, 2016-present). It deliberately reports **no**
lines, because a schedule feed holds none and `base.py` is explicit that
guessing `is_closing` corrupts CLV downstream — so college football cannot be
graded and stays off Live under the rule above. It also models FBS-vs-FBS
only: an opponent-adjusted rating for an FCS team that plays the division once
is an estimate of nothing, and those games cluster on exactly the opening
weekend where the board is busiest. Its team names do NOT match the odds
board's ("Akron" vs "Akron Zips", "San José State" vs "San Jose State
Spartans"); join on the ESPN `game_id`, which our own `data/capture/ncaaf/`
already carries.

## 11. If you take one thing from this document

The technical barrier in this category is low — the site is static files and
the model is a few hundred lines. The scarce thing is **a record that can be
checked.**

Every competitor advantage we have comes from being willing to publish numbers
that make us look ordinary. The moment the app claims an edge we haven't
measured, we become the thing we were built to replace, and we lose the only
asset we have.

Build the UI so that the losses are as easy to find as the wins.
